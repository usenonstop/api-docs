## Cadastro

Os webhooks são cadastrados pelo próprio anunciante, no painel da nonStop:
**Configurações → Webhooks**
([usenonstop.com/configuracoes?tab=webhook](https://www.usenonstop.com/configuracoes?tab=webhook)).
A aba aparece para contas com plano ativo.

São duas listas:

| Lista | Eventos |
| --- | --- |
| **Webhooks de imóveis** | [`publication:create`, `publication:delete`, `property:update` e `property:delete`](/versions/unstable/webhooks/property) |
| **Webhooks de leads** | [`lead:create`](/versions/unstable/webhooks/lead) |

Para cada endpoint são três campos:

- **Url**: endereço completo, com `https://`. Endereços internos (`localhost`, redes
  privadas, IP de metadados de nuvem) são recusados ao salvar.
- **Token**: opcional. Vai no header `Authorization`.
- **Secret**: opcional. Assina cada envio com HMAC-SHA256.

Preencha pelo menos um dos dois últimos. Veja **Autenticação** abaixo.

Dá para cadastrar mais de um endpoint por lista. Não dá para escolher eventos: cada
endpoint recebe todos os da sua lista, e quem separa é o campo `event` do corpo.

## Requisição

Cada evento é um `POST` com o corpo em JSON. Os formatos estão em
[Imóvel](/versions/unstable/webhooks/property) e [Lead](/versions/unstable/webhooks/lead).

```http filename="requisição" copy
POST /webhooks/nonstop HTTP/1.1
Content-Type: application/json
Authorization: Bearer <token cadastrado>
X-Nonstop-Signature: sha256=<HMAC-SHA256 do corpo com a secret cadastrada>

{"event":"property:update","property":{"id":"6650f1c2a8b4e93d7c1a2b3c", ...}}
```

O `Authorization` só vai quando há token cadastrado, e o `X-Nonstop-Signature` só
quando há secret.

## Autenticação

São dois mecanismos. Dá para usar um, o outro ou os dois juntos:

- **Token**: todo envio leva o header `Authorization: Bearer <token>`.
- **Secret**: todo envio leva o header `X-Nonstop-Signature` com a assinatura
  HMAC-SHA256 do corpo. A secret nunca vai na requisição, então quem vê um envio
  (num log, num proxy) não consegue forjar outro.

Sem nenhum dos dois, o envio sai sem autenticação.

- **Os dois são seus.** São segredos que você inventa e cadastra junto da URL, sem
  relação com o token da API da nonStop. Use valores longos e aleatórios, como a
  saída de `openssl rand -hex 32`, e use `https`.
- **Não há IP fixo.** Os envios saem de infraestrutura de nuvem sem faixa de IP
  publicada, então liberar por IP não funciona. Valide pelo token ou pela assinatura.

### Token

Responda `401` ao que chegar sem o header ou com outro valor.

``` ts filename="app/api/webhooks/nonstop/route.ts" copy
import { timingSafeEqual } from "node:crypto";

const expected = Buffer.from(`Bearer ${process.env.NONSTOP_WEBHOOK_TOKEN}`);

export async function POST(request: Request) {
  const received = Buffer.from(request.headers.get("authorization") ?? "");
  const authorized =
    received.length === expected.length && timingSafeEqual(received, expected);
  if (!authorized) return new Response(null, { status: 401 });

  const body = await request.json();
  switch (body.event) {
    case "publication:create":
    case "property:update":
      // grava ou atualiza body.property, com body.property.id como chave
      break;
    case "publication:delete":
    case "property:delete":
      // tira do ar body.propertyId
      break;
    case "lead:create":
      // cria body.lead no seu CRM, com body.lead.id como chave
      break;
  }

  return new Response(null, { status: 204 });
}
```

### Assinatura (HMAC)

O header é `X-Nonstop-Signature: sha256=<hex>`: `sha256=` seguido do HMAC-SHA256 do
corpo, em hexadecimal minúsculo, com a secret como chave. É o mesmo formato do
`X-Hub-Signature-256` do GitHub e da Meta, só com outro nome de header.

- **Calcule sobre o corpo cru**, exatamente como chegou, antes do parse do JSON.
  Parsear e serializar de novo muda os bytes (acentos, espaços), e a assinatura
  deixa de bater.
- **A chave é a secret como texto**, do jeito que foi cadastrada, sem decodificar hex
  ou base64.
- **Compare em tempo constante**, como no exemplo abaixo.

Para testar o seu verificador antes de cadastrar:

```txt filename="vetor de teste" copy
secret: segredo_de_teste
corpo:  {"event":"lead:create","lead":{"id":"123","name":"João"},"userSlug":"exemplo"}
header: X-Nonstop-Signature: sha256=777e58fcba6e57afa3bba767718ce7a9b53aea3608a3d1fc1a7a7f397fd172ce
```

``` ts filename="app/api/webhooks/nonstop/route.ts" copy
import { createHmac, timingSafeEqual } from "node:crypto";

export async function POST(request: Request) {
  // O corpo CRU: a assinatura é sobre estes bytes, não sobre o JSON parseado.
  const raw = await request.text();
  const expected = Buffer.from(
    "sha256=" +
      createHmac("sha256", process.env.NONSTOP_WEBHOOK_SECRET!)
        .update(raw)
        .digest("hex"),
  );
  const received = Buffer.from(request.headers.get("x-nonstop-signature") ?? "");
  const valid =
    received.length === expected.length && timingSafeEqual(received, expected);
  if (!valid) return new Response(null, { status: 401 });

  const body = JSON.parse(raw);
  // daqui em diante, o mesmo `switch (body.event)` do exemplo do token

  return new Response(null, { status: 204 });
}
```

## Entrega

- **Qualquer resposta `2xx` em até 5 segundos** conta como entregue. O corpo da
  resposta é ignorado. Se o processamento for demorado, enfileire do seu lado e
  responda antes.
- **Redirecionamentos** são seguidos até 3 vezes, repetindo o mesmo `POST` com os
  mesmos headers, inclusive o `Authorization` e o `X-Nonstop-Signature`. Cadastre a
  URL final.
- **Falhou** (status fora de `2xx`, timeout ou erro de conexão)? O evento entra numa
  fila e é reenviado a cada 5 minutos, até 3 vezes. Depois disso, é descartado.

### Repetição e ordem

O mesmo evento pode chegar mais de uma vez: basta você processar e responder depois
dos 5 segundos. E um reenvio pode chegar depois de um evento mais novo do mesmo
imóvel, porque ele leva o conteúdo do momento em que o evento nasceu, não o atual.

- Processe de forma idempotente, com `property.id` / `propertyId` (imóveis) e
  `lead.id` (leads) como chave.
- Num `property:update`, compare `property.updatedAt` com o que você já tem e
  descarte o mais antigo.

## Falhas seguidas

Cada falha conta contra o endpoint, e uma entrega bem-sucedida zera a contagem.

- **1ª e 2ª falha:** o e-mail da conta recebe um aviso com o endpoint e o erro.
- **3ª falha:** o endpoint é **removido** da lista, e o e-mail da conta recebe o
  aviso da remoção. A partir daí, nada mais é enviado para ele.

Depois de uma falha, as que vierem nos 10 minutos seguintes não contam: um lote de
eventos que falha junto porque o seu servidor caiu gasta um aviso, não os três. Ou seja, para
ser removido, o endpoint precisa falhar em três momentos diferentes, com pelo menos
10 minutos entre eles e nenhuma entrega bem-sucedida no meio.

Para voltar a receber, cadastre o endpoint de novo: salvar zera a contagem. Os
eventos do período em que ele esteve fora não são reenviados. Para recuperar o
estado, use a [API de imóveis](/versions/unstable/apis/property).

## Quem recebe cada evento

- **`publication:create` / `publication:delete`**: a conta em cujo **próprio site**
  o imóvel entrou ou de onde saiu, inclusive quando sai sozinho porque foi vendido
  ou ficou indisponível. Tirar o imóvel de um portal não gera evento.
- **`property:update`**: as contas que têm o imóvel publicado no próprio site.
- **`property:delete`**: as contas que tinham o imóvel em qualquer integração, site
  ou portal. Pode chegar para um `propertyId` que você nunca recebeu; nesse caso,
  ignore.
- **`lead:create`**: a conta responsável pela lead. Se ela for de corretor vinculado
  a uma imobiliária, o evento vai **só** para os webhooks da imobiliária, e o
  `userSlug` diz qual corretor recebeu. Com o
  [atendimento por IA](/versions/unstable/webhooks/ia) ligado, os webhooks de leads
  da imobiliária recebem só as leads que vão para a IA.

<Callout type="info">
  **Um endpoint para vários clientes.** Se você integra mais de uma conta, pode
  cadastrar a mesma URL em todas, com o mesmo token e a mesma secret. Quando mais
  de uma delas tem o mesmo imóvel, o evento chega uma vez só, assinado com a secret
  de uma delas. Por isso a secret tem que ser a mesma. Use o `userSlug` dos eventos
  de publicação e de lead para saber de qual conta ele é.
</Callout>

## Como testar

- **Imóveis:** coloque um imóvel no site e tire em seguida. Chegam um
  `publication:create` e um `publication:delete`.
- **Leads:** crie uma lead pela [API de leads](/versions/unstable/apis/lead). Ela
  gera um `lead:create`, mas é uma lead de verdade: entra no CRM da conta e avisa o
  responsável por WhatsApp e e-mail. Com o
  [atendimento por IA](/versions/unstable/webhooks/ia) ligado, a lead da API não gera
  o evento: teste com o serviço desligado.
