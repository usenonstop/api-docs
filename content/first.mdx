## Token

Para obter o token da nonStop vá para [https://www.usenonstop.com/configuracoes?tab=integration](https://www.usenonstop.com/configuracoes?tab=integration). Na seção **Integrações** você irá encontrá-lo. Ele será
utilizado para identificar o solicitante e a validade de seu plano. Caso você suspeite que seu token esteja comprometido você pode subustituí-lo apertando o botão de refresh no canto
superior direito.

### Um token = uma conta

O token é o **único** identificador do anunciante: toda rota responde sempre com os
imóveis da conta dona do token, e não existe parâmetro de query que troque de conta.

Se você atende vários clientes, precisa de **um token por cliente** — o de cada um,
pego na conta dele. Usar o seu próprio token para ler os dados de um cliente não dá
erro: a API responde normalmente, só que com os imóveis da **sua** conta. É por isso
que o sintoma aparece como número que não fecha (a API devolve mais — ou menos —
imóveis do que o cliente vê no painel dele), e não como falha de autenticação.

## Requisições

A URL base é: https://www.usenonstop.com/api

As requisições feitas para as APIs da nonStop deverão utilizar nos headers o campo:  
  
Authorization: Bearer [token]



### Chame o host com `www` — o apex derruba o seu token

Repare no `www` da URL base. Ele não é decorativo: chamar `https://usenonstop.com`
(sem `www`) faz toda requisição autenticada falhar, **mesmo com um token
perfeitamente válido**.

O apex responde `308` redirecionando para `https://www.usenonstop.com`. Como os dois
são domínios diferentes, seu cliente HTTP **remove o header `Authorization` ao seguir
esse redirecionamento** — é comportamento de especificação, não bug do cliente, e vale
para `fetch`, `curl`, `Go net/http`, `requests` do Python e `axios`, entre outros.

O resultado é que a API recebe uma requisição sem credencial nenhuma e responde:

Status: 400 — `{"error":"token inválido"}`

Que é exatamente a mesma resposta de um token expirado ou errado. Por isso o sintoma
engana: a mensagem acusa o token, mas o token está certo — o que se perdeu foi o
header, no meio do caminho.

Dá para confirmar em dez segundos. As duas chamadas abaixo usam o **mesmo** token e a
**mesma** rota; a segunda só acrescenta a flag que força o `curl` a manter o header
através do redirecionamento:

``` bash copy
# sem www: o header se perde no 308
curl -sL -H "Authorization: Bearer $TOKEN" \
  "https://usenonstop.com/api/unstable/imoveis/todos?perPage=1"
# {"error":"token inválido"}

# mesmo token, forçando o header a sobreviver ao redirecionamento
curl -sL --location-trusted -H "Authorization: Bearer $TOKEN" \
  "https://usenonstop.com/api/unstable/imoveis/todos?perPage=1"
# {"properties":[...],"total":2873,"advertiser":{...}}
```

Não use `--location-trusted` como solução — ela reenvia sua credencial para qualquer
destino do redirecionamento, o que é justamente o risco que a regra existe para evitar.
A correção é apontar direto para o host final: **sempre `https://www.usenonstop.com/api`**,
nunca confie no redirecionamento em chamada autenticada.
